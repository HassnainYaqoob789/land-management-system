ASystem architecture

Four layers. The browser talks only to the Next.js application. Every API call passes the five protect() checks and runs as one database transaction tagged with the signed-in user, so PostgreSQL itself enforces province scope, approval rules and the audit trail. External services sit on the right.

Preparer cannot approve. The person who prepared or raised a record cannot decide any of its approvals.
One person, one tier. Nobody can approve two stages of the same record.
Position decides. Only the holder of the stage's position (Approval Matrix), in their own provinces.
Finance verifies, Manager Land releases. The releaser cannot be the verifier; a hold blocks both.

EControls built into the system

These rules are enforced by the server and the database, not only by the screens.

1
Province isolation

Row-level security in PostgreSQL: each user sees only the provinces assigned to them. A record outside scope answers 404.

2
Separation of duties

Preparer cannot approve; one person decides one tier; only the position holder decides. sod_mode = strict, admin override off.

3
MFA and re-auth

TOTP or passkey for sensitive permissions; re-authentication within 10 minutes for privileged actions.

4
Audit trail

audit.audit_event is append-only: no UPDATE or DELETE. Every change records who, when and what.

5
PII masking

CNIC, phone and bank details need pii:read; auditor and administrator see CNIC masked.

6
WHT filer / non-filer

FBR withholding tax is computed in the database from policy; non-filer rate is 2× the filer rate. Client rates are never trusted.

7
Payment holds

Court stay order, deceased owner (until Wirasat / Intiqal), lease hold and landowner hold block verify and release.

8
Budget check

A voucher is verified only if the project budget can cover it.

9
Award cap

Vouchers on a case cannot exceed its payable award (unreversed vouchers counted, case row locked). Idempotency keys stop duplicates.
